Question 1:
(a) 1. Composition (what UI to show), 2. Layout (where to place it), 3. Drawing (how it renders).
(b) The Layout phase has two steps: Measure and Place.
(c) LazyColumn's composition depends on its parent's layout phase because it needs to know its available size (measured during Layout) to determine how many items to compose. Example: an Instagram feed where items are composed only when they become visible on the screen.
(d) Compose is fast because of "Skipping". If the state hasn't changed, Compose skips the phases for those elements.

Question 2:
(a) Row measures Image -> Row measures Column -> Column measures Text A -> Column measures Text B -> Column decides its size -> Row decides its size -> Row places Image -> Row places Column -> Column places Text A -> Column places Text B.
(b) Column size: 100x40. Row size: 148x48.
Positions (x,y): Image (0, 0), Column (48, 0), Text A (48, 0), Text B (48, 20).
(c) Each node is visited exactly once (Single pass measurement). If measured twice at each level, the traversal time would grow exponentially (O(2^n)), causing UI lag.
(d) This tree is produced by the Composition phase. Each node contains a LayoutNode (rules for measuring/placing) and drawing instructions.

Question 3:
(a) Yes, they are equivalent. The read happens when the state is used (in the body of the composable for Snippet 2, and explicitly via .value in Snippet 1).
(b) Text("A"): read in Layout phase (inside offset lambda). Text("B"): read in Composition phase. When offsetX changes, Text("A") only triggers Layout and Draw phases. Text("B") triggers Recomposition, Layout, and Draw.

Question 7:
Prediction & Result (Canvas): The state `color` is read inside the `drawRect` lambda of the Canvas, which executes ONLY during the Drawing phase. Therefore, tapping the button skips Composition and Layout entirely. Logcat only shows "draw".
Experiment Result (Box with background): When replacing the Canvas with `Box(Modifier.background(color))`, the state is read during the Composition phase (to build the modifier). Now, tapping the button triggers "composition", "layout/measure", "layout/place", and "draw".
Conclusion: The difference tells us that a recomposition or phase restart depends entirely on WHERE the state is READ (used), not where it is stored or created.

Question 10:
Explanation: In the naive version, reading `listState.firstVisibleItemIndex` directly in the composition means the UI recomposes every time a new item becomes visible (dozens of times during a fast scroll).
By wrapping it in `derivedStateOf`, Compose filters the changes. It only triggers a recomposition when the boolean RESULT of the condition (`> 0`) changes. This only happens twice: when scrolling down past the first item (false -> true) and when returning to the top (true -> false).

Question 11:
Explanation: By passing `count` as a lambda (`{ count }`), the state is no longer read in the body of the `Parent` function. Therefore, `Parent` is no longer in the restart scope of that state. The state is only read inside `Child`, making `Child` the only restart scope. When tapping "Add", only `Child` recomposes, while `Parent` and `Sibling` are successfully skipped.

Question 12:
Frame 1: Composition reads imageHeightPx = 0. Top padding of text is 0.dp. During Layout phase, `onSizeChanged` fires with height=360 and updates the state. A recomposition is scheduled. The frame is drawn with the text overlapping the image (padding is 0).
Frame 2: Composition runs again, reading imageHeightPx = 360. Top padding is set correctly. Layout and Draw happen normally, and the text is pushed down.
(a) `toDp()` is a warning sign because it implies taking a raw pixel measurement from the layout phase and feeding it back into a modifier (composition phase).
(b) The dangerous 3-step pattern: Read state in composition -> Measure element in layout -> Update that same state in layout (triggering a backward loop).
(c) This breaks the Unidirectional Data Flow principle.

Question 14:
Result: In Logcat (tag:StackBelow), we see exactly TWO "measure child" lines followed by exactly ONE "place children" line.
This perfectly demonstrates the "one pass" rule: every child is measured exactly once before the parent decides its size and moves to the placement step.
